Firestore Security Rules

Security rules define who has access to read and write records in our Cloud database. Copy these into your Firebase console:

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /employees/{employeeId} {
      // Allow read/write access to any authenticated user
      allow read, write: if request.auth != null;
    }
  }
}

Rationale:

This rule ensures that any database request must carry a valid JSON Web Token (JWT) indicating the user is logged in. Unauthenticated users (non-logged-in visitors) trying to bypass the client-side code will be blocked by Firestore's server-side access control lists (ACL).

Viva Q&A Quick Reference

Q1: What cloud model is used here?

Answer: Backend-as-a-Service (BaaS), a subset of PaaS (Platform-as-a-Service). We utilize Firebase for database and authentication without managing servers, databases, or writing backend scripts.

Q2: What is Cloud Firestore?

Answer: Cloud Firestore is a flexible, scalable NoSQL document database. Data is stored in documents containing key-value pairs, which are organized into collections. There are no tables, rows, or foreign keys.

Q3: How does Firestore differ from a SQL database?

Answer: Firestore is NoSQL. It does not require a predefined schema. It stores data as JSON-like documents, allows deep nested arrays/objects, offers automatic horizontal scaling, and has built-in real-time listener capabilities, whereas SQL databases like MySQL are schema-bound, vertically scalable, and require a middleware server.

Q4: How does authentication work?

Answer: Firebase Auth processes credentials (email/password) on secure Google servers, returns a JSON Web Token (JWT) to the client browser, and maintains the login state automatically in IndexedDB/LocalStorage. It securely transmits this JWT during Firestore calls to verify credentials against safety rules.
